# InsureRAG 市场与 GitHub 调研及产品差异化建议

调研日期：2026-10-08。本文是研究和产品建议，不修改已确认的 V1 开发规格。后续 Agent 不得把本文的候选增强项自动视为已批准范围。

## 1. 结论与研究边界

市场和 GitHub 均存在相关产品。当前规划足以形成业务试点，但“保险问答 + 采集 + 推荐 + 转人工”的功能组合，已经有直接商业参照。Agent、RAG、私有部署和双端界面不能单独证明差异化。

建议探索的定位：**可本地部署、结论有条款依据、顾客与员工协同的保险选购与咨询工作台**。最先强化“比较是否可信、咨询是否有效推进、员工是否能接着办”三个环节。

这不是已验证的市场空白。比较、引用和交接已有厂商提供；可能的竞争力来自这些能力在特定保险服务商、具体产品资料、本地资源约束下的准确性、可用性与交付成本，需要试点验证。

研究使用厂商官网、GitHub 仓库说明及许可证。商业功能代表厂商公开描述，未购买或试用付费产品，未独立验证宣传效果、客户规模或准确率。GitHub 项目未部署、未运行测试、未完成安全审计；没有把 README 的 production-ready 当作独立结论。一次公开资料调研不代表穷尽市场。本次未核实统一报价、具体合同和大陆本地部署可用性，不据此判断哪个商业产品最便宜。

市场判断（基于以上样本的推论）：保险知识助手已有充分供给；可审阅的文档结果、业务记录、任务推进及系统衔接，是值得学习的产品组织方式。公开资料不足以证明中小服务商存在未被满足的付费需求，仍需访谈。

## 4. GitHub：更值得借鉴的通用工程

| 项目 | 适合参考的部分 | 与现有路线的关系 |
| --- | --- | --- |
| [LangGraph](https://github.com/langchain-ai/langgraph) | 有状态流程、持久化恢复、人工介入 | 继续作为自研编排基础；有长期记忆能力不代表必须启用 |
| [Dify](https://github.com/langgenius/dify) | 工作流、知识库、模型配置、运行可观测性 | 用作平台能力和操作体验参照，不必为增加功能整体迁移 |
| [FastGPT](https://github.com/labring/FastGPT) | 知识库处理、RAG、可视化工作流 | 借鉴员工配置知识和检查检索结果的体验 |
| [RAGFlow](https://github.com/infiniflow/ragflow) | 文档理解、分块检查、证据定位、Agentic 检索 | 重点比较保险 PDF、表格和引用体验；是否替换现有链路需样本评测 |

Chatwoot 的自动分配等能力不等于我们需要照搬。当前仍遵守公共队列、员工主动接单、单一负责人、所有员工可见机构客户的既定规则。

- [RAGFlow LICENSE](https://raw.githubusercontent.com/infiniflow/ragflow/main/LICENSE)：Apache-2.0。
- [Chatwoot LICENSE](https://raw.githubusercontent.com/chatwoot/chatwoot/develop/LICENSE)：核心适用 MIT；enterprise 目录另有许可，第三方组件保留各自许可。
- [Dify LICENSE](https://raw.githubusercontent.com/langgenius/dify/main/LICENSE)：基于 Apache-2.0 的附加条件，涉及多租户及前端标识，不宜简写为无附加条件的 Apache-2.0。

## 5. 当前项目“朴素”的具体原因

当前代码的核心仍是文档上传、检索和问答；销售助手业务在规格中，不能把设计当成已经实现。现有规格已包含业务规则、证据引用、字段确认、人工交接和发布版本，比单纯聊天机器人更完整。

真正的产品缺口可分为三类：

1. **首个使用场景过宽**：保险公司、代理服务商、多险种都支持，是架构目标，但不足以说明首批客户为何购买。保险公司销售自有产品，与代理机构跨公司比较的业务目标不同。
2. **成果不够具体**：回答完后，顾客究竟看懂哪些取舍？员工究竟省下哪项重复工作？应给出可编辑、可交接、可复核的结果。
3. **优势缺少可证明性**：支持 RAG 或 Agent 只是实现方式。需要用真实或明确标注的测试资料，证明复杂条款、缺失条件、版本冲突和人工交接都处理得当。

建议保持多险种扩展结构，但首轮演示选择一个险种、少量经核对的产品和一条完整咨询路径。此建议不改变“不锁定单一险种”的既定范围，也不把演示数据视为真实可售目录。

## 6. 三个最值得强化的方向

### 6.1 可解释、可核查的产品比较

V1 已有推荐规则与引用；建议提升为可操作的比较工作区：

- 按顾客真正关心的条件组织比较，而非只显示模型概括。
- 每一项比较能打开对应产品、文档版本、页码和原文片段。
- 清楚区分“资料明确支持”“需要补充条件”“资料未说明”“规则不匹配”。没有资料不等于没有保障，也不等于符合条件。
- 推荐说明同时回答：为何进入候选、哪些需求得到满足、有哪些重要限制、还有什么未确认。
- 不用没有校准依据的“适合度 95 分”掩盖缺失证据；不把候选推荐等同于承保或理赔结论。

界面示例仅表示设计，不描述真实产品：顾客问“同样是医疗保障，A 和 B 到底有什么差别？”工作区同时显示关键条款差异、适用条件与证据。点击“我更重视续保条件”后调整比较重点，保留依据和未确认项。

工程依赖：统一产品字段、条款定位、版本绑定、确定性规则输出、前端比较卡片。先实现少量重要维度，避免对整份文档承诺完美语义理解。

### 6.2 能推进咨询的信息采集

V1 已有可配置表单和字段确认；建议让问题选择与推荐实际关联：

- 已明确的信息不重复问；冲突信息先确认，不静默覆盖。
- 优先追问会改变候选集合或重要解释的缺失条件。
- 顾客可以跳过问题，系统展示由此产生的比较限制。
- 只有业务确实需要且完成相应告知同意时，才进入健康信息采集。
- 资料卡区分顾客确认事实、尚待确认的模型提取和内部备注。

例如地区缺失影响可售范围时，先解释为何需要地区；无需在咨询开头收集整套身份与健康资料。客户改变一个偏好后，只重算受影响的规则和展示。

工程依赖：字段依赖关系、缺失与冲突状态、规则执行轨迹、受限工具调用。初期可用确定性优先级选择问题，不需要额外“问题规划 Agent”。

### 6.3 员工接手即可工作的咨询档案

V1 已有接单、聊天及跟进；建议让工作台围绕一个咨询事项组织：

- 顾客确认的需求与业务资料。
- 看过的候选产品、比较维度和已解释的限制。
- 仍未解决的问题、资料缺口和客户表达的顾虑。
- 证据与产品版本，AI 已给出的建议以及员工修订记录。
- 当前负责人、服务状态和下一次跟进事项。

顾客端呈现简明可理解的比较与摘要；员工端呈现完整依据、内部备注和待办。内部内容不得混入顾客展示。电话和微信仍只记录跟进，不能据此扩展为自动联系。

可以增加可编辑的咨询摘要/方案说明页，再按需增加导出。这是一份可复核的业务产物，不承诺自动生成正式投保建议书或报价。

## 7. 第二阶段值得探索的增强

| 候选能力 | 价值假设 | 主要难点 | 顺序建议 |
| --- | --- | --- | --- |
| 产品资料整理工作台 | 降低服务商整理产品与条款的时间 | 从 PDF 提取候选字段、关联证据、冲突提示和人工纠正 | 核心咨询闭环完成后优先；仍由有权限员工直接发布，不增加审核人 |
| 条款版本变化影响提示 | 产品更新后可定位受影响的知识、规则与历史推荐 | 条款映射、依赖索引、失效处理，不能自动把旧结论改成新结论 | 高价值但工程较重，第二阶段 |
| 场景化条款解释 | 顾客更容易理解保障适用条件 | 同时处理限制、例外与未知信息，防止模拟被误当保证 | 小范围验证，不能推演为实际核保/理赔承诺 |
| 销售问答陪练 | 帮助新员工熟悉产品和常见异议 | 评价依据与产品知识一致，避免单纯追求促成 | 有业务闭环后再考虑；市场已有类似能力 |
| 报价与投保连接器 | 将咨询延伸到交易 | 合作方、真实接口、业务资质及可靠性 | 遵守原决定，仅预留边界 |

## 8. 技术路线是否要因此改变

没有必要因为竞品功能多就放弃 LangGraph，或再引入一套通用 Agent 平台。建议仍然采用已确认的模块化系统：

顾客/员工前端 → FastAPI 业务接口 → LangGraph 编排 → 产品与规则服务、知识检索、咨询记录及人工服务工具。

模型负责理解、提取候选信息和解释；规则负责明确条件判断；数据库负责已确认业务事实与服务状态；界面负责让人看懂并操作结果。LangGraph checkpoint 用于当前任务恢复，不必建设跨会话自由积累的 Agent 长期记忆。

复用现有 PDF/OCR、混合检索、重排和模型服务，再补齐产品数据与证据契约。复杂任务可以在同一图中分阶段执行，不要求每个步骤都是独立模型 Agent。对本地模型尤其应测量模型调用次数、排队时间及失败行为。

“5 名员工、10 位顾客同时咨询”是试点目标，不等于单张 GPU 同时执行 10 次生成。4060 移动端和 4070 Ti 桌面端能承载的模型、上下文与吞吐仍需实测；本文没有给出保证。

## 9. 建议的落地优先级

| 阶段 | 可演示、可验收的结果 | 与已确认 V1 的关系 |
| --- | --- | --- |
| 第一阶段 | 一组产品从资料发布、顾客咨询、候选推荐到人工接单完整走通 | 完成既定 V1 核心；优先打通而非扩大功能 |
| 第二阶段 | 对比每项有依据；能显示未知和重要限制；顾客修改需求可重算 | 深化引用、规则及表单体验，部分属于新增交互 |
| 第三阶段 | 员工接手获得完整咨询档案，可修订摘要、记录下一步 | 深化双端协作，可选新增摘要产物 |
| 第四阶段 | 产品资料整理更省力，更新能提示影响 | 新增增强范围，需另行纳入开发计划 |

暂不优先：为了宣传增加 Agent 数量、长期记忆、数字人、自动外呼、大而全 CRM、多地区规则、没有合作接口的交易演示。这些不能代替当前核心价值验证。

## 10. 商业定位仍需通过访谈验证

建议分别访谈保险公司销售/运营人员和代理机构负责人，不把两类需求混为一谈。可以先各找少量有真实业务经验的人，展示同一条咨询路径，追问：

1. 最近一次解释产品、比较条款或接手顾客时，最费时间的具体步骤是什么？
2. 现有工具怎样完成它，哪里必须重新抄录或翻文档？
3. 愿不愿意提供脱敏产品资料和真实问题，让我们比较处理结果？
4. 谁使用、谁采购、谁维护资料？独立部署和本地模型是硬条件还是偏好？
5. 哪个可观察的改善足以支持付费试点？

用相同任务比较人工流程和试用流程：完成一份可用比较的时间、需要人工纠正的内容、重要遗漏、无证据结论、接手时仍需重复询问的字段。先记录基线，再商定目标，本文不编造提升百分比。

建议首个展示任务：顾客表达保障需求 → 系统识别关键缺失条件 → 展示少量候选与证据 → 顾客调整需求 → 更新比较 → 员工接单继续处理。这个流程可以在不增加报价、不增加长期记忆、不调用云端模型的情况下检验产品价值。
